# Publication Content Contract Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the Phase 1 publication content contract and a deterministic, network-free TypeScript validator/exporter that fails closed before any Batch-02 content or reader application is added.

**Architecture:** Add an isolated Node/TypeScript package at `tools/publication-contract/`. Zod schemas are the executable contract and generate versioned JSON Schema files under `publication/contract/v1/schema/`; the human-visible rubric catalog lives beside them. A manifest-driven validator loads only explicit files from `publication/`, applies cross-record scientific/publication policies, and exports a sorted immutable intermediate bundle through a fresh staging directory.

**Tech Stack:** Node.js 24, TypeScript, Zod 4, `yaml` 2, Node's built-in test runner, SHA-256 from `node:crypto`.

**Execution constraints:**

- Obtain explicit operator approval before installing npm dependencies. No dependency is installed as part of writing this plan.
- Do not modify the existing Python registry validator or its tests.
- Do not normalize Batch-02 scientific content, generate the invention, build Astro/Pagefind, add GitHub Actions, or deploy anything in this plan.
- Do not infer scientific approval. Only `publicationState: approved` records explicitly listed in `publication/manifest.yaml` are eligible.
- Keep `publication/manifest.yaml` empty at the end of Phase 1. Fixtures demonstrate behavior without publishing scientific content.
- Never publish automatically. The exporter only writes an intermediate bundle to a caller-selected local directory.
- Commit commands below are optional checkpoints. Run them only if the user explicitly authorizes commits.

  records: z.array(ManifestEntrySchema),
  pages: z.array(ManifestEntrySchema),
  assets: z.array(ManifestEntrySchema),
}).strict();

export type PublicationManifest = z.infer<typeof PublicationManifestSchema>;

  "process-ease",
  "resource-burden",

  "regulatory-clarity",
  "validation-maturity",
] as const;

export const CriterionIdSchema = z.enum(CRITERION_IDS);

const RubricBandSchema = z.object({
  score: z.number().int().min(1).max(5),
  label: z.string().min(1),
  definition: z.string().min(1),
}).strict();

export const RubricCatalogSchema = z.object({
  schemaVersion: z.literal(1),
  rubricVersion: z.string().regex(/^\d+\.\d+\.\d+$/),
  criteria: z.array(z.object({
    id: CriterionIdSchema,
    title: z.string().min(1),
    description: z.string().min(1),
    higherIsMoreFavorable: z.literal(true),
    unknownRule: z.string().min(1),
    bands: z.array(RubricBandSchema).length(5),
  }).strict()).length(8),
}).strict().superRefine((catalog, ctx) => {
  const criterionIds = catalog.criteria.map((criterion) => criterion.id);
  if (new Set(criterionIds).size !== CRITERION_IDS.length) {
    ctx.addIssue({ code: "custom", message: "each approved criterion must appear exactly once" });
  }
  for (const criterion of catalog.criteria) {
    const scores = criterion.bands.map((band) => band.score);
    if (scores.join(",") !== "1,2,3,4,5") {
      ctx.addIssue({ code: "custom", message: `${criterion.id} bands must be ordered 1 through 5` });
    }
  }
});

const AssessmentBaseSchema = z.object({
  schemaVersion: z.literal(1),
  kind: z.literal("assessment"),
  id: StableIdSchema,
  title: z.string().min(1),
  publicationState: PublicationStateSchema,
  methodId: StableIdSchema,
  criterionId: CriterionIdSchema,
  rubricVersion: z.string().regex(/^\d+\.\d+\.\d+$/),
  supportingClaimIds: z.array(StableIdSchema),
  conflictingClaimIds: z.array(StableIdSchema),
  reviewer: z.string().min(1),
  reviewDate: IsoDateSchema,
}).strict();

export const AssessmentRecordSchema = z.discriminatedUnion("status", [
  AssessmentBaseSchema.extend({
    status: z.literal("scored"),
    score: z.number().int().min(1).max(5),
    label: z.string().min(1),
    rationale: z.string().min(1),
    basis: z.enum(["source-supported", "inference", "ai-assessed-human-reviewed"]),
  }).strict(),
  AssessmentBaseSchema.extend({
    status: z.literal("unknown"),
    unknownReason: z.string().min(1),
  }).strict(),
  AssessmentBaseSchema.extend({
    status: z.literal("not-applicable"),
    notApplicableReason: z.string().min(1),
  }).strict(),
]);

## Errata: Implementation divergences from this plan

This section records where the shipped implementation deliberately differs from the
plan above. It was added after the Phase-1 acceptance gate, on 2026-11-16, and does
not change the plan's intent; it makes the difference auditable.

1. **Unknown-command diagnostic code.** The CLI sketch in Task 1 (line 215) and the
   Task 2 note (line 724) name `CLI_COMMAND_NOT_IMPLEMENTED`. The shipped CLI uses a
   single canonical `CLI_UNKNOWN_COMMAND` for both the command guard and the
   unreachable default branch, so there is exactly one unknown-command outcome.

2. **The rubrics catalog is mandatory.** `validate` and `export` require
   `contract/v1/rubrics.yaml`. A missing catalog fails with `RUBRICS_REQUIRED` and a
   schema-invalid catalog with `RUBRICS_INVALID`. Semantic validation is never
   silently skipped, because a skipped check would report a false `VALID`.

3. **Two additional derivative diagnostics.** `SOURCE_DERIVATIVE_PATH_INVALID` and
   `SOURCE_DERIVATIVE_HASH_MISMATCH` are not in the Task 6 diagnostic list. They were
   added because a derivative path and a derivative hash were otherwise unchecked,
   which left a private repository path and an unchecked hash able to reach
   `records.json`. This is required by the Phase-1 criterion that private paths and
   bad hashes fail before output replacement.

4. **One stricter, undeclared rule.** `RELATIONSHIP_TARGET_KIND_MISMATCH` enforces the
   `targetKind` that the plan's own relationship schema already declares, so an edge
   may not point at a record of the wrong kind. The plan's diagnostic list does not
   name it; it is strictly more conservative than the plan.

5. **"Design section 13.1" does not exist in this document.** The Phase-1 completion
   criteria and Task 10 Step 2 refer to a fail-closed branch list in "design spec
   section 13.1". This file is the approved design spec and contains no section 13.
   The branch-by-branch inspection it asks for was performed against the executable
   source instead, and its result is recorded in `state/session-log.md` and in
   `state/workflow.yaml`.
